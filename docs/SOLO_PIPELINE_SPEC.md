# Word Labs SOLO Tracker — Unit Generation Pipeline Spec

This document is the durable handoff for building a new SOLO Tracker unit. It was
originally drafted in claude.ai against a *mental model* of the product; it has
since been **rewritten to match the actual code** (`solo/index.html`) after Units
24–27 were built and Unit 28 reached Stage 0. Where the original draft and the
real codebase disagreed, the codebase won.

**Ground-truth principle:** every SOLO outcome ultimately answers to a NSW
Mathematics K-10 Syllabus (2022) content point — not to a DoE lesson, not to a
resource, not to this spec. DoE units and slides are *evidence* that a content
point is being taught well; they are not the target. Where Green-band outcomes
extend beyond Stage 3, they map to **Stage 4 group A** content points explicitly
(the earlier/more accessible tier — not Stage 4 B), not to vague "extension"
framing.

---

## 0. The two deliverables

A finished unit produces **two** things. Don't conflate them — they live in
different places and serve different audiences.

### Deliverable A — In-app SOLO Tracker content (the primary deliverable)

The playable unit students and teachers actually use, authored as data inside
**`solo/index.html`** (one file, React-via-Babel, no build step) plus the
Supabase `resources` table. This is how Units 24–27 exist. **This is what
"building a unit" primarily means.** Full process in Section 3.

### Deliverable B — Teacher-facing program document (parallel artifact)

A landscape A4 Word program (`Maths_S3_YearB_Unit{NN}_SOLO_Full_Program.docx`)
generated by `scripts/build_program_template.js` from a `unit_data.js` file, plus
an optional resource appendix. This is a **planning/evidence document** for the
teacher (and for NSW DoE reviewers) — it does not drive the app. Units 24–27 did
not have one; from Unit 28 on, Nicholas wants it generated alongside the in-app
content. Full process in Section 5.

Both deliverables are built from the **same approved rubric** (Stage 0) and the
same syllabus mapping, so they stay consistent.

```
  SOLO Units/Unit {NN}/
    DoE Unit {NN}.zip                 (contains Mathematics-Stage3-Unit{NN}.docx + lessons + resources)
    DoE Slides {NN}.zip
  Syllabus/
    Maths K-10 Syllabus 2022.pdf
  u{NN}/
    00_rubric_draft.md                ← Stage 0 output. Background source, untracked by design.

units/                                ← Deliverable B output (docx). Tracked in git.
  u{NN}/
    unit_data.js
    Maths_S3_YearB_Unit{NN}_SOLO_Full_Program.docx
    Unit{NN}_Resource_Appendix.docx   (optional)
    PROGRESS.md

docs/
  SOLO_PIPELINE_SPEC.md               ← this file. Tracked.

scripts/
  build_program_template.js           ← the docx template engine. Tracked.
```

**`SOLO Units/` is gitignored** — NESA syllabus content and NSW DoE unit/slide
material aren't Nicholas's to redistribute via a public repo. The `SOLO Units/u{NN}/`
rubric also lives here intentionally: it's the *background source* used to build
everything else and doesn't need to be tracked. It must exist physically in the
Codespace, but is never pushed.

**`solo/index.html` is the real checkpoint for Deliverable A.** Because the
in-app build is committed to `main` (Vercel auto-deploys), git history *is* the
durable record of build progress. A per-unit `units/u{NN}/PROGRESS.md` (tracked)
remains the human-readable log of what's done vs in-flight (Section 8).

## 2. Stage 0 — Rubric extraction and band classification

Reproduces, as an automated/verifiable process, what was previously done by hand
in EduChat. **This stage is unchanged from the original spec and was validated on
Unit 28 — keep it.**

### 0a. Extract success criteria

For every lesson in the DoE unit `.docx`, find the success-criteria statements.
**Note (learned on Unit 28):** this DoE template puts SC inside **tables** (the
cell header reads "Students can:"), *not* under a literal "Students can"
paragraph heading — so `python-docx`'s `.paragraphs` stream misses them. Read
`document.tables` instead; the same LI/SC table cell also conveniently carries
DoE's own sub-strand label (e.g. "Geometric measure A") and the matching syllabus
content points, which makes 0b mostly a confirmation pass.

Extract each SC verbatim, without the "Students can" prefix, de-duplicated into a
flat pool with the lesson(s) each appears in noted.

### 0b. Classify each success criterion against syllabus content points

Identify the Stage 3 sub-strand + content point for each SC (Represents Numbers,
Additive/Multiplicative Relations, Fractions, Geometric Measure, 2D/3D Spatial
Structure, Non-Spatial Measurement, Data, Chance — each split into content groups
**A** and **B**).

**Band rule (validated on Unit 28):** the syllabus splits each sub-strand into
content groups **A** and **B**. In practice for these Stage 3 Year B programs:

- **Red** = content **group A** (≈ Year 5 material — prior-year, folded in for
  consolidation). e.g. "Position A", "Chance A".
- **Yellow** = content **group B** (≈ Year 6 — the home-year content for the
  program being built). e.g. "Position B", "Chance B".
- **Green** = beyond Stage 3 → **Stage 4 group A** content (see 0d).

The original spec warned at length not to conflate the content-group letter (A/B)
with the two-year teaching cycle. Nicholas's clarification (2026-06-19) is that
for these units the practical mapping **A → Year 5 → Red, B → Year 6 → Yellow**
does hold — confirm it per unit against the DoE unit's own framing (which content
it treats as *prior learning* vs *new core learning*), but it's a reliable
starting point, not a trap.

### 0c. Modality (hands-on) flag — informational only for Deliverable A

Tag each SC written/digital-appropriate, hands-on-required, or hands-on-preferred.
**In the in-app SOLO tracker every outcome is digital** (MC/input questions +
"try it in your book" Grow steps + Beyond bookwork projects), so this tag does
**not** change the in-app structure — it informs *how a Grow lesson is written*
(e.g. a reflection outcome might say "fold the paper to check the flip"). It
matters more for Deliverable B's lesson cards (which can list physical materials).
Treat the tags as suggestions; the author chooses.

### 0d. Green band — Stage 4 group A extension

For the most advanced content, generate "next steps" from genuine **Stage 4 group
A** content points (quote the actual content point + outcome code, e.g.
`MA4-PRO-C-01`, `MA4-LIN-C-01`). Use the **A** tier of each Stage 4 focus area,
not B — B is too far past the year level. (Unit 28 example: Probability A
sample-space / P(event) / relative-frequency, *not* Probability B complementary
events; Linear relationships A plotting/recognising, *not* B graphical solution
of equations.)

### 0e. Output + gate

A draft rubric (`SOLO Units/u{NN}/00_rubric_draft.md`) grouped by band: per
outcome a code (Rn/Yn/Gn), a one-line student-voice descriptor, the band, the
modality note, and the cited content point.

**Gate:** Nicholas reviews — especially A/B band assignment and that Green's
Stage 4 **A** content points are real and appropriately pitched — before any
content is built. An error here propagates through both deliverables.

## 3. Deliverable A — Building the in-app unit (`solo/index.html`)

This is the heart of the work, per the battle-tested `project_solo_unit_workflow`.
**Completeness bar (Unit 26 gold standard):** a unit is NOT done at "verified
resources". Every outcome (red/yellow/green) must also have a full guided **Grow**
lesson with a 3-step hint ladder on every try-it. Match Unit 26.

### 3.1 Gap analysis (do FIRST, every time)

Map **every** rubric success criterion to an outcome in a table. Watch for
criteria silently folded into another outcome's label but never given their own
outcome. Some criteria can't be tested digitally — note and skip. Red =
recall/foundational, Yellow = applying, Green = extending (Stage 4 A; cull to the
~5–6 most practical next steps if Green has 20+ points). Since Stage 0 already
maps SC → outcomes → content points, this is largely confirmation.

### 3.2 The six data structures (all keyed by unit id `uNN`)

Author all six in `solo/index.html`:

1. **`UNITS`** — array. Each unit `{id:"uNN", name, subtitle, outcomes:[...]}`.
   Each outcome `{id, band:"red"|"yellow"|"green", short, label, questions:[10]}`.
   Render is **by band then array order** — place outcomes red→yellow→green.
   The 10 questions are the **Show** assessment.
2. **`PRETESTS`** — `{uNN:[{outcomeId, short, questions:[2]}]}`. 2 per outcome;
   both correct auto-ticks the outcome.
3. **`PRACTICE`** (the **Know** section) — keyed `uNN_oid:{example:[3-5 strings],
   questions:[~9]}`. Immediate feedback, no rubric effect; `example` teaches first.
4. **`RESOURCES`** — keyed `uNN_oid:[{label, url, type:"video"|"worksheet"|"website"}]`,
   2–4 per outcome. **See 3.4 — DB vs code is a real gotcha.**
5. **`BEYOND`** — keyed `uNN:{resources:[Stage 4 links], projects:[{icon, title,
   description, tasks:[5-6]}]}` for the ⭐ Beyond SOLO tab. ~4 real-world
   multi-step project tasks done in books.
6. **`LEARN`** (the **Grow** guided lesson) — keyed `uNN_oid`, for **every**
   outcome. Schema:
   ```js
   LEARN.uNN_oid = {
     journey: "Chance",                          // strand label in the lesson header
     hook:    {question, reveal, revealLabel?},  // curiosity Q → predict in book → reveal
     watch:   {count, prompts:[...]},            // what to look for in the video(s)
     workedExample: {problem, steps:[...]},      // step-reveal model
     tryIt:   [{question, answer, explain, hints:[3]}],  // self-check in book; hints = nudge→strategy→worked
     reflect: {prompt, note}                     // finish-the-sentence + "one thing you learned"
   };
   ```
   `LEARN[key].hook` present → full-screen guided lesson (Hook→Learn→Try→Reflect,
   Coach, progress dots, "I'm stuck" hint ladder). Every `tryIt` MUST have an
   authored 3-step `hints` ladder (NOT AI-generated).

Also update **`UC`** (unit colour theme `uNN:{bg,border,text,dot,dark}`) and the
landing/rubric tab gating (`unit.id==="uNN"` lists) — confirm both exist for the
new unit.

**Free, engine-level (no per-unit work):** the Grow Reflect note + end-of-Show
assessment reflection (both with "Send to my teacher"), the shared exit dialog,
and teacher-visible reflection panels all work for any unit automatically. The
only per-unit reflection work is writing good `reflect` prompts in each LEARN
lesson. (Requires `solo_reflections` + `solo_assessment_reflections` tables —
migrations already run.)

### 3.3 Question + content conventions

- Outcome IDs are **database keys** (`solo_progress`, `solo_show_completions`).
  **Never renumber existing IDs** — students lose progress. Appending new outcomes
  to an existing unit → append IDs (r7, y4…). Band grouping in render keeps columns
  right regardless of ID order.
- Question types: `mc` (answer ∈ options[], no dup options), `input` (answer +
  `aliases[]` — always add `$`, comma, decimal-trailing-zero, fraction/mixed-number
  variants), `truefalse`, `order` (items[] + answer[] same set). Unicode minus −
  for negatives. Australian context: AUD, GST 10%, km/m/kg/g, Aus spelling.

### 3.4 Resources — TWO sources, know which is canonical (real gotcha)

The app renders `fetchedRes = unitResources[key].length>0 ? unitResources[key] :
RESOURCES[key]` — i.e. rows in the Supabase **`resources` table OVERRIDE** the
hardcoded `RESOURCES` in code. The app only **reads** that table. History: u24/u25
curated in the DB; u26/u27 curated in code (stale DB seeds were deleted so they
fall back to the verified code set). Before trusting/editing a unit's resources,
check the DB: `GET {supabase}/rest/v1/resources?unit_id=eq.uNN` with the anon key
(anon can't write — DB changes go via the Supabase SQL editor / staging CSV +
Section 6). Decide per unit which source is canonical and keep all resources there.

### 3.5 Resource sourcing + the VERIFICATION gate (mandatory)

Target 2–4 per outcome: YouTube videos (year-5/6 for red/yellow, year-7/Stage-4
for green/Beyond — Math with Mr J, Corbettmaths, Mathspace, Periwinkle, Matholia,
WorksheetCloud, Khan; Eddie Woo for AU-specific) + Corbettmaths PDF worksheets
students print and do in books. No duplicate URLs within one outcome.

Verification is a **gate, not best-effort**:
- **Videos:** WebFetch can't read YouTube titles (JS-rendered). Use the oEmbed API
  `https://www.youtube.com/oembed?url=https://www.youtube.com/watch?v=ID&format=json`
  — returns exact title+author for live videos, errors for dead/private. Batch ~12
  in parallel. Confirms existence AND that the label matches content.
- **PDFs/websites:** bulk `curl -o /dev/null -w "%{http_code}" -L -A "Mozilla/5.0"`.
  404 = replace (find the right Corbettmaths file).
- **Content-match + level cross-check:** the resource must address the *specific*
  Stage 1 content point, at genuine Year 6 / Stage 3 level (cross-check against the
  DoE unit's own resources or a second AU source — matters most for Green, which
  has no DoE anchor).
- **No silent duplicates; record what couldn't be verified** (dead/paywalled/
  ambiguous → it doesn't go in; flag the gap rather than guessing).

### 3.6 Maths verification

Write Node scripts that `eval` each of the six blocks out of the HTML, then
auto-check: MC answer ∈ options + no dup options; pure arithmetic; %-of,
remainders, conversions, substitution, distributive expansion, factors/primes/
multiples, like-terms. Crude regex flags many false positives — manually confirm
each flag against the full expression. Manually read the conceptual ones scripts
can't mark (place-value naming, number-line, word→algebra, rates).

### 3.7 Finish gate

- All six blocks `eval`/Babel-compile cleanly — **0 console errors via Playwright
  is the real gate** in this no-test app.
- Every outcome has pretest + practice + resources + a complete LEARN lesson with a
  3-step hint ladder on every try-it (no gaps — the Unit 26 bar).
- Commit + push to `main` (repo convention for solo work — direct to main, Vercel
  auto-deploys). Co-author line: `Claude Opus 4.8`.

## 4. Stage — Resource staging + Supabase promotion (for DB-canonical units)

When a unit's resources are canonical in the DB (the u24/u25 pattern), stage them
first, gate, then promote — don't insert blind:

**Staging file** `units/u{NN}/03_resources_staged.csv`:
```
unit_id, outcome_id, type, label, url, scope, class_id
```
- `type`: video / website / game / worksheet
- `scope`: "global", `class_id`: null
- `unit_id`: **always with the `u` prefix** (`'u28'`) — matching Supabase
  convention. (An insert without the prefix silently creates orphaned rows.)

**Gate:** Nicholas spot-checks a sample; all rows fetch-verified per 3.5.

**Promote** (only after the gate, via the Supabase SQL editor — anon key can't
write):
```sql
DELETE FROM resources WHERE unit_id = 'u{NN}';
INSERT INTO resources (unit_id, outcome_id, type, label, url, scope, class_id)
VALUES (...);  -- from the approved staging CSV
```
For code-canonical units (u26/u27 pattern) this stage is skipped — resources live
in the hardcoded `RESOURCES` block and there must be **no** DB rows for that unit
(or the stale DB rows win).

## 5. Deliverable B — Teacher-facing program document

Generated by `scripts/build_program_template.js` from a `units/u{NN}/unit_data.js`
file matching the **UNIT DATA SCHEMA** documented at the bottom of that script.
Build the `unit_data.js` from the approved rubric + Stage 1 mapping (outcome →
content point → DoE lesson). Build once the in-app outcomes/content points are
settled, so the two deliverables agree.

### Document structure (landscape A4)
- **Page 1** — two-column: outcomes/content points/teaching model (left); Working
  Mathematically / differentiation / pre-test / post-test / resources (right).
- **Page 2** — Outcome Teaching Record: one row per outcome (outcome sequence, not
  calendar order), content point text, mini-lesson ref, sign/date columns.
- **Pages 3+** — Mini Lesson Sequence: one card per lesson (banner, metadata, DoE
  link bar only if a real DoE source exists — never fabricate one, LI/SC, 4-step
  teaching structure, vocab, differentiation, assessment, teaching-notes field).

### Hands-on lessons (per the Stage 0c tag)
For outcomes tagged hands-on-required/preferred, the card's teaching steps should
name actual physical materials (grid paper, geoboards, nets, mirrors, balance
scales, bags of counters), the Resources line should list them, the Assessment
field should describe what's physically produced/demonstrated, and it's fine for
the lesson to run longer. Set `is_hands_on: true` + `materials: [...]` in the
lesson data. Matters most for Geometric Measure / Spatial Structure / mass &
capacity — check the tag, don't assume by strand name.

### Build conventions (docx-js — see `/mnt/skills/public/docx/SKILL.md`)
- Landscape A4 content width 15038 DXA (16838 − 900×2 margins).
- `ShadingType.CLEAR`, never `SOLID`. Tables need `columnWidths` on the table AND
  `width` on every cell.
- Band colours: Red `C00000`/`FCDBD9`, Yellow `7F6000`/`FFF9E6`, Green
  `375623`/`EBF3E6`, Navy header `1F3864`.
- Write the build script to disk via Python (not bash heredocs) to avoid encoding
  corruption. Convert via `soffice.py --headless --convert-to docx` and run
  `validate.py` before treating it as done — table issues only surface after the
  LibreOffice round-trip.
- Page-1 Term field stays blank unless Nicholas confirms term placement.

### Optional resource appendix
`Unit{NN}_Resource_Appendix.docx` — full resource table + worksheet download
checklist. Worksheet PDFs can't be fetched server-side (Corbettmaths 403s
non-browser requests); the appendix produces a clean download checklist, and PDF
merging happens only after Nicholas manually downloads/re-uploads the files.

| Stage | Output | Gate before proceeding |
|---|---|---|

the review-file stage and expensive to catch after they're live across many units.

## 7. The syllabus + DoE source as evidence (Stage 1, lightweight)

For Deliverable B's lesson cards (and to sanity-check Deliverable A), record per
outcome: the exact NESA content point (quoted, with sub-strand code), and the DoE
lesson(s) that teach it (lesson number + one-line summary). It's fine — normal for
Green — for an outcome to have **no** DoE lesson; say so rather than inventing one.
One DoE lesson can cover multiple outcomes and vice versa; record that explicitly.
Because Stage 0 already records the content point against each SC, this is a
confirmation pass plus the DoE-lesson lookup, not mapping from scratch.

## 8. Context limits, checkpointing, resuming mid-unit

A full unit build (Stage 0 → both deliverables) is far more than one context
window — especially the per-outcome content authoring in Section 3. Treat
approaching the context limit (~last 3%) as a trigger to **checkpoint, not push
on**:

1. Finish the current atomic unit of work (e.g. finish the outcome currently being
   authored/verified) — don't start a new outcome there isn't room to finish.
2. Update `units/u{NN}/PROGRESS.md` (tracked) — what's done, in-flight, next, **by
   outcome code**.
3. Leave partial output clearly partial, not silently incomplete (e.g. a staging
   CSV with only the verified rows, and PROGRESS.md saying which).
4. **Commit the checkpoint.** For Deliverable A, that means committing the
   in-progress `solo/index.html` + PROGRESS.md. An uncommitted checkpoint provides
   no protection against a Codespace rebuild.
5. Stop. Don't squeeze in "just one more" outcome — that's exactly how unverified
   shortcuts slip in.

### PROGRESS.md format
Append-only running log at `units/u{NN}/PROGRESS.md`:
```markdown
# Unit {NN} — Progress Log

## Session 1 — {date}
- Stage 0: complete + approved. Rubric in SOLO Units/u{NN}/00_rubric_draft.md.
  Decisions: A→Red/B→Yellow confirmed; Green = Stage 4 A; build both deliverables.
- Next: gap analysis + start in-app authoring (UNITS/PRETESTS first).

## Session 2 — {date}
- Deliverable A: UNITS + PRETESTS authored for R1–Y6 (9 outcomes); G1–G3 not started.
  RESOURCES verified for R1–R3 (oEmbed/curl logged). LEARN: R1, R2 done.
- Stopped: context limit mid-authoring.
- Next: resume at R3 LEARN. Do NOT re-verify R1–R3 resources — already confirmed.
```

Key habits: always say what's done **by outcome code**; always say what gate (if
any) is being waited on; never silently re-do completed work; one PROGRESS.md per
unit. This applies *within* a stage too (e.g. which outcomes are authored vs
verified), not just between stages.

## 9. Decisions captured (why the spec reads this way)

| Decision | Reason |
|---|---|
| In-app content is the primary deliverable | Units 24–27 are six JS structures in `solo/index.html`; that's what students use. The original spec centred on a Word doc that no live unit had. |
| Program docx kept as parallel Deliverable B | Nicholas wants it from Unit 28 on (teacher planning / NSW evidence), generated alongside the in-app content from the same rubric. |
| Green = Stage 4 **A** content | Stage 4 B is too far past Year 6; A is the right extension pitch (confirmed Unit 28). |
| Band A→Red (Year 5), B→Yellow (Year 6) | Syllabus content groups A/B map in practice to the consolidation vs home year for these Year B programs (confirmed Unit 28). Verify per unit against the DoE unit's prior-vs-new framing. |
| Rubric stays in gitignored `SOLO Units/u{NN}/` | It's background source used to build everything else; doesn't need tracking. The real tracked checkpoint is `solo/index.html` git history + `units/u{NN}/PROGRESS.md`. |
| Resource DB-vs-code canonicality is explicit | The app lets DB `resources` rows override hardcoded `RESOURCES`; mixing them silently breaks units (stale u26/u27 DB seeds had to be deleted). |
| oEmbed for video verification | WebFetch can't read JS-rendered YouTube titles; oEmbed returns exact title/author and errors on dead/private videos. |
